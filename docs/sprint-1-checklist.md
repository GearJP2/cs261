## 1. เป้าหมายและขอบเขต

เมื่อจบ Sprint ผู้ใช้ที่เข้าสู่ระบบต้องดูสนามและเวลาเปิด–ปิด ดูโปรไฟล์ ส่งคำขอเข้าร่วม Party เป็น `Pending` ได้ และ Host ต้องแก้ไขหรือยกเลิก Party ได้ โดยตรวจสิทธิ์และเวลานัดหมายที่ Backend

**US1 ยืนยันแล้ว:** เข้าสู่ระบบและยืนยันบัญชีนักศึกษามหาวิทยาลัยธรรมศาสตร์ รวมออกจากระบบ; Priority High, Estimate 3 points ตามที่ทีมระบุ ดู [User Story และ Acceptance Criteria](user-stories.md) เป้าหมายเดโมรวม login สำเร็จ/ล้มเหลวและ logout ส่วนช่องทางเชื่อมมหาวิทยาลัยจริงยังต้องตรวจสอบ

เอกสารนี้ใช้ Story ที่เกียร์ให้ครบ US1–14 และกติกาจาก `user_story_tasks.txt` ฉบับแก้ แล้วเพิ่มงานพื้นฐาน งานเชื่อมต่อ และช่องติดตาม Task ที่เรียบเรียงตามรูปแบบทีมอยู่ใน `docs/tasks.md` โดยคงไฟล์ต้นทางไว้ รายชื่อและความถนัดอัปเดตตามทีมยืนยัน: กอล์ฟกับพีทำ Backend, โกลถนัดฐานข้อมูล, วี/เนท/ออสตินทำส่วนอื่น และเกียร์ช่วยได้ทุกส่วน การแบ่งงานย่อยด้านล่างเป็นข้อเสนอสำหรับ Sprint นี้

## 2. แบ่งทีมตามความถนัด: 3 คู่ + เกียร์ช่วยข้ามส่วน

| ทีม | สมาชิก | งานหลัก | ผู้ตรวจเพิ่มเติมที่ไม่ได้ร่วมเขียน |
| --- | --- | --- | --- |
| คู่ A — Backend | กอล์ฟ + พี | Logic, API, สิทธิ์ และ Backend tests ของทุก US ใน Sprint; พีนำ US3/US8 กอล์ฟนำ US7/US9-B2 พีนำ US1 โดยกอล์ฟช่วยตรวจและเกียร์ช่วยเชื่อม provider | เกียร์ หรือโกลสำหรับส่วนข้อมูล |
| คู่ B — UI/Frontend | วี + เนท | ออกแบบหน้าเว็บและเชื่อม API; วีนำ US7 และ US1 เนทนำ US3/US8 ช่วยตรวจ UI ให้กัน | ออสติน หรือเกียร์ |
| คู่ C — Database และหน้าสนาม | โกล + ออสติน | โกลนำ schema/migration/seed ทุก US; ออสตินนำ UI/Frontend ของ US9 และช่วยทดสอบ โกลช่วยด้านข้อมูล ออสตินช่วยตรวจ flow/ข้อมูลตัวอย่าง | คู่ A ตรวจข้อมูล; คู่ B ตรวจ UI |
| ผู้ช่วยข้ามส่วน | เกียร์ | Setup, contract ร่วม, integration, review และช่วยแก้งานที่ติดขัดทั้ง Frontend/Backend/Database | ผู้ที่ไม่ได้ร่วมเขียนในส่วนนั้น |

สมาชิกครบ 7 คน: **กอล์ฟ, พี, วี, เนท, ออสติน, โกล และเกียร์** ใช้ชื่อเกียร์ตามที่ยืนยัน แม้ task เก่าจะเขียนว่าเกีย และใช้วีแทน V ในเอกสารนี้

การจัดวี/เนท/ออสตินลง UI และ Testing เป็นข้อเสนอจากความต้องการให้ทำส่วนอื่น สามารถสลับงานออกแบบ หน้าเว็บ และทดสอบกันได้ โดยไม่เปลี่ยนคู่ Backend ของกอล์ฟกับพี

### วิธีทำงานเป็นคู่และข้ามคู่

- คู่ A ทำ Backend ร่วมกัน สลับผู้เขียน/ผู้ตรวจตาม task; ไม่บังคับให้คนที่อยากทำ Backend ต้องย้ายไป Frontend
- คู่ B ช่วยกันออกแบบและเชื่อมหน้าเว็บ ส่วนคู่ C จับคู่ตรวจข้อมูลและ flow สนาม แม้งานหลักของโกลกับออสตินต่างกัน
- แต่ละ task มีชื่อหลัก/ผู้ช่วยในตารางแล้ว; หากผู้ช่วยอยู่ต่างคู่ ให้จับคู่ส่งต่องานตาม dependency โดยคงคู่หลักของทีมไว้
- งาน Database ของ US3/US7/US8 อยู่ใน BASE-02 และ migration ที่โกลดูแล ส่วน logic อยู่กับคู่ A; US9-B1 แยกเป็น task ของโกลโดยตรง ทุกการแก้ schema ต้องประสานโกลก่อน
- เปิดงานพัฒนาหลักไม่เกินหนึ่ง task ต่อคน และส่ง PR ย่อยเร็วเพื่อไม่ให้ Backend หรือฐานข้อมูลกลายเป็นจุดรอของทุกหน้า
- เกียร์ช่วยงานที่ติดขัดและรวมระบบ แต่ทุกคนยังต้องทดสอบงานของตนเอง ไม่ส่งการทดสอบทั้งหมดให้เกียร์คนเดียว
- ผู้ร่วมเขียนช่วยตรวจระหว่างทำงานได้ แต่ PR ต้องมีผู้ตรวจที่ไม่ได้ร่วมเขียนเพิ่มอย่างน้อยหนึ่งคน เกียร์ไม่จำเป็นต้องตรวจทุก PR
- เมื่อทราบช่องทางเชื่อมมหาวิทยาลัย ให้ประเมินภาระพีและวีใหม่ หากหนักเกินให้เกียร์ช่วยพัฒนาหรือสลับงานกับคนที่ว่าง และพิจารณาลด scope ก่อนเพิ่มงานนอก Sprint

## 4. Checklist งานพื้นฐานร่วมกัน

รายการนี้เป็นงานสนับสนุน Sprint เพิ่มจาก task เดิม ไม่ใช่ User Story ใหม่

- [ ] **BASE-01 — Setup:** ทำให้โครงแอปและ PostgreSQL รันได้จริง ล็อก dependencies มี `.env.example` ที่ไม่มีค่าลับ และบันทึกคำสั่งติดตั้ง/migrate/run/test — เกียร์ จับคู่กับโกล และประสานคู่ A
- [ ] **BASE-02 — Schema/Contract:** โกลออกแบบและทำ migration ของ User, Sport, Party, Membership และ JoinRequest รวม constraint ป้องกันคำขอซ้ำ; ตกลงความสัมพันธ์ Venue/OpeningHours เพื่อส่งต่อ US9-B1 และให้คู่ A/B/C ตกลง API/request/response/error กับวิธีตรวจผู้ใช้ปัจจุบันร่วมกัน — โกลนำ กอล์ฟช่วย เกียร์ประสาน
- [ ] **BASE-03 — Test data:** เตรียม Host, ผู้ใช้ทั่วไป, สมาชิกเดิม, สนามเปิด/ปิด และ Party เปิดรับ/เต็ม/เริ่มแล้ว/ยกเลิก พร้อมคำสั่งสร้างข้อมูลซ้ำได้ — โกล จับคู่กับออสติน
- [ ] **BASE-04 — Shared access:** ใช้ session/การตรวจสิทธิ์จาก US1 และทำจุดเข้าหน้ารายละเอียด Party/โปรไฟล์ขั้นต่ำ; fixture session ใช้ปลดล็อกการทดสอบได้ แต่ไม่ปิด US1 แทนการเชื่อมจริง — พี จับคู่กับเกียร์ และให้วี/เนทช่วยจุดเข้าหน้าเว็บ

ผลส่งมอบ BASE-02 ต้องระบุว่าแต่ละคู่จะเรียกใช้ฟังก์ชันหรือ API ใด ไม่จำเป็นต้องบังคับทุกหน้าให้เป็น REST API หากทีมเลือก Django Templates แต่ต้องมีข้อตกลงข้อมูลและข้อผิดพลาดที่ตรงกัน

### US1 — Login และยืนยันบัญชีนักศึกษาธรรมศาสตร์ (พี + วี; โกล/เกียร์ช่วย)

**Priority:** High • **Estimate:** 3 points (ตามทีมระบุ; ไม่ใช่จำนวนวัน)

ในฐานะนักศึกษาธรรมศาสตร์ที่มีบัญชีมหาวิทยาลัย ต้องการเข้าสู่ระบบด้วยบัญชีที่ยืนยันตัวตนได้อย่างปลอดภัยและออกจากระบบได้ เพื่อเข้าใช้งานตามสิทธิ์นักศึกษาและป้องกันคนนอก

- [ ] **US1-D — Design:** วีออกแบบหน้า Login, loading/error และ Logout; พี/เกียร์ตรวจช่องทางที่มหาวิทยาลัยอนุญาต รวมหลักฐานสถานะนักศึกษา, callback และ session flow
- [ ] **US1-B — Backend:** พีเชื่อม provider ที่อนุญาต ตรวจตัวตนและสิทธิ์นักศึกษา ผูก local user ด้วยตัวระบุที่เชื่อถือได้ สร้าง/ยกเลิก session และทำ API-01 `/me`; โกลดู mapping และกอล์ฟช่วยตรวจ
- [ ] **US1-F — Frontend:** วีเชื่อม flow Login แสดงข้อผิดพลาดโดยไม่เก็บรหัสผ่านมหาวิทยาลัยใน browser storage; สำเร็จไปหน้าหลัก; ปุ่ม Logout กลับหน้า Login
- [ ] **US1-T — Testing:** ออสติน/เกียร์ทดสอบสอง Scenario ที่ทีมให้: ข้อมูลถูกต้องสร้าง session และเข้าหน้าหลัก, ข้อมูลผิดไม่มี session; เพิ่มกรณี Logout, session หมดอายุ และบัญชีไม่มีสิทธิ์นักศึกษาตามข้อเสนอทดสอบใน Technical Plan

**ตรวจรับตาม Story:** Login สำเร็จเมื่อยืนยันตัวตนและสิทธิ์ได้จริง; ข้อมูลผิดต้องแจ้งเตือนและเข้าไม่ได้ รวมถึง Logout ได้ตาม I want การผ่าน mock provider อย่างเดียวไม่ทำให้ US1 Done

**สิ่งที่ยังรอ:** protocol/provider, credentials สำหรับแอป และหลักฐานที่มหาวิทยาลัยให้ใช้ยืนยันว่าเป็นนักศึกษา การมีชื่อโดเมน email มหาวิทยาลัยอย่างเดียวไม่ใช่ข้อสรุปว่ายังมีสิทธิ์นักศึกษา

### US3 — ขอเข้าร่วม Party (พี + เนท; โกลช่วยข้อมูล)

**Priority:** High • **Estimate:** 5 points ตามต้นทาง

- [ ] **US3-D — Design:** ออกแบบปุ่มขอเข้าร่วม สถานะ Loading/Pending และข้อความเมื่อสำเร็จ เต็ม ส่งซ้ำ หรือเริ่มแล้ว
- [ ] **US3-B — Backend:** ตรวจ login, Party เปิดรับ/ยังไม่เริ่ม/มีที่ว่าง และไม่เป็นสมาชิกอยู่แล้ว; บันทึกคำขอ Pending โดยไม่เพิ่มสมาชิกหรือหักที่ว่าง พร้อมป้องกันคำขอซ้ำรวมถึงส่งพร้อมกัน
- [ ] **US3-F — Frontend:** เชื่อมคำขอ แสดงผลจาก Backend เปลี่ยนปุ่มเป็นรออนุมัติ ป้องกันกดซ้ำ และแสดง Pending เดิมได้เมื่อเปิดหน้าใหม่
- [ ] **US3-T — Testing:** ทดสอบ Pending และจำนวนที่ว่างคงเดิม, ส่งซ้ำ/ส่งพร้อมกัน, สมาชิกเดิม, ไม่ login, Party เต็ม/เริ่มแล้ว/ยกเลิก และเรียก Backend โดยตรง

**ตรวจรับ:** ผู้ใช้ส่งคำขอแล้วเห็น Pending; ในฐานข้อมูลไม่มีสมาชิกใหม่หรือที่ว่างลดลง; คำขอซ้ำไม่สร้างรายการเพิ่ม และ Party ที่ไม่เปิดรับถูกปฏิเสธ โดยยังไม่ต้องมีหน้าจออนุมัติ US10

### US7 — Host แก้ไขหรือยกเลิก Party (กอล์ฟ + วี)

**Priority:** High • **Estimate:** 8 points ตามต้นทาง

- [ ] **US7-D — Design:** ออกแบบฟอร์มแก้ไข หน้าต่างยืนยันยกเลิก และ contract ของการแก้ไข/ยกเลิก ระบุเงื่อนไขสถานะตาม PLAN-05
- [ ] **US7-B — Backend:** ตรวจว่าเป็น Host ของ Party นั้น ตรวจข้อมูลและช่วงเวลาเปิดสนามด้วยตัวตรวจ US9 แล้วบันทึก; การยกเลิกเปลี่ยนเป็น Cancelled และหยุดรับคำขอใหม่
- [ ] **US7-F — Frontend:** แสดงเครื่องมือจัดการเฉพาะ Host โหลดค่าปัจจุบัน บันทึกการแก้ไข พร้อมยืนยัน/ยกเลิกการยกเลิก Party และแสดงผลผิดพลาดจาก Backend
- [ ] **US7-T — Testing:** ทดสอบ Host แก้ไข/ยกเลิกสำเร็จ, กดไม่ยืนยันแล้วข้อมูลไม่เปลี่ยน, ข้อมูลผิด/เวลาไม่เปิด, ผู้ไม่ใช่ Host และไม่ login เรียก Backend โดยตรง รวมถึง US3 ส่งคำขอหลังยกเลิก

**ตรวจรับ:** Host แก้ไขข้อมูลที่ถูกต้องได้ คนอื่นแก้ไม่ได้ เวลาที่สนามปิดถูกปฏิเสธ และ Party ที่ยกเลิกแล้วไม่รับคำขอใหม่

### US8 — ดู User Profile (พี + เนท)

**Priority:** High • **Estimate:** 1 points ตามต้นทาง

- [ ] **US8-D — Design:** ออกแบบหน้าโปรไฟล์และกำหนดข้อมูลที่เปิดเผยได้ ได้แก่ ชื่อ กีฬาที่สนใจ และคะแนนเครดิต พร้อมกรณีข้อมูลว่าง/ไม่พบผู้ใช้
- [ ] **US8-B — Backend:** ตรวจ login ดึงโปรไฟล์ตาม User ID ส่งเฉพาะฟิลด์ที่เปิดเผยได้ และจัดการไม่พบผู้ใช้; ใช้ค่าเครดิตที่จัดเก็บไว้โดยไม่เพิ่มระบบคำนวณ US14
- [ ] **US8-F — Frontend:** กดชื่อแล้วเปิดโปรไฟล์ถูกคน แสดงข้อมูลจาก Backend พร้อม loading/not found/error และสถานะเมื่อยังไม่มีข้อมูล
- [ ] **US8-T — Testing:** ทดสอบผู้ใช้หลายบัญชี ข้อมูลตรง ID ข้อมูลว่าง/ไม่พบผู้ใช้/ไม่ login และตรวจว่า response ไม่มีรหัสผ่าน session token หรือข้อมูลลับ

**ตรวจรับ:** เปิดโปรไฟล์จากชื่อผู้ใช้แล้วเห็นข้อมูลของคนนั้นครบตามขอบเขต และ API ไม่เปิดเผยฟิลด์ส่วนตัวนอก contract

### US9 — สนามและเวลาเปิดให้บริการ (โกล + ออสติน; กอล์ฟทำ Backend)

**Priority:** High • **Estimate:** 5 points ตามต้นทาง

- [ ] **US9-D — Design:** ออกแบบหน้าดูสนามและส่วนเลือกสนามในหน้าสร้าง Party ให้เลือกกีฬา ดูเวลาเปิด–ปิด และเห็นคำเตือนเมื่อเลือกเวลาที่ใช้ไม่ได้
- [ ] **US9-B1 — Database:** สร้างข้อมูลสนาม กีฬาที่รองรับ และตารางวันเวลาเปิด–ปิด พร้อม migration และข้อมูลตัวอย่างที่ตรวจสอบได้
- [ ] **US9-B2 — Backend:** ดึงสนามตามกีฬา/ตารางเปิด–ปิด และสร้างตัวตรวจร่วมสำหรับช่วงเริ่มถึงสิ้นสุดกิจกรรม ปฏิเสธช่วงที่ไม่อยู่ในเวลาเปิดทั้งช่วง ใช้ร่วมกับการสร้างและแก้ไข Party
- [ ] **US9-F — Frontend:** เชื่อมสนามตามกีฬา แสดงเวลาเปิด–ปิด ป้องกันเลือกช่วงใช้ไม่ได้ และแสดงข้อผิดพลาดจาก Backend; ส่งส่วนเลือกสนามให้ผู้ทำหน้าสร้าง Party และคู่ B ใช้
- [ ] **US9-T — Testing:** ทดสอบข้อมูลสนามตรงกีฬา นัดในช่วงเปิด วันปิด ก่อนเวลาเปิด สิ้นสุดหลังเวลาปิด ช่วงเวลาไม่ถูกต้อง และการส่งค่าผิดผ่าน Backend โดยตรง รวมทั้งการสร้าง/แก้ไขที่เกี่ยวข้อง

**ตรวจรับ:** ข้อมูลสนามตรงกีฬาและเวลาทำการ; Backend ตรวจตลอดช่วงนัดหมาย ไม่พึ่งการปิดปุ่มในหน้าเว็บอย่างเดียว และ US7 ใช้กฎเดียวกัน

**Dependency ที่ต้องปิด:** task เดิมของ US9 รวมการเชื่อมหน้าสร้าง Party หน้านี้อยู่นอก US1 และหากยังไม่มี ให้บันทึกงานส่วนนี้ว่า Blocked หรือให้ทีมตกลงแยกไป Sprint ถัดไปอย่างชัดเจน ห้ามถือว่า US9 ครบตาม task เดิมเพียงเพราะทดสอบ component แยกได้

## 7. Branch และ PR สำหรับทำเป็นคู่

- แตก branch จาก `main` ที่อัปเดตแล้วตามชิ้นงาน เช่น `feat/us-3-join-request`, `feat/us-7-edit-cancel-party`, `feat/us-8-profile`, `feat/us-9-venue-hours` และ `chore/sprint-1-setup`
- ถ้า pair programming ให้สลับผู้เขียนและ push ทีละคน ถ้าเขียนแยกเครื่องพร้อมกันให้แยก branch ย่อย เช่น `feat/us-9-venue-data` และ `feat/us-9-venue-ui` เพื่อลดการชนกัน
- PR ระบุรหัส task จากเอกสารนี้ สิ่งที่เปลี่ยน วิธีทดสอบ และงานที่ยังรอ ห้ามปิดทั้ง US เมื่อส่งเฉพาะ UI หรือ Backend
- ใช้ Commit Convention และ review ตาม [README](../README.md) เช่น `feat(party): add pending join requests`
- จองผู้แก้ schema/migration ร่วมกันก่อนเริ่มงาน ให้โกลตรวจ migration และเกียร์ช่วยจัดลำดับ merge; ทุกคู่รับผิดชอบแก้ conflict และทดสอบส่วนของตน
- หากอัปเดตไฟล์ checklist พร้อมกัน ให้แก้เฉพาะแถวของตนและดึงฉบับล่าสุดก่อนส่ง PR

## 8. รวมระบบและตรวจรับ Sprint

- [ ] **INT-01 — Integration:** รวมงานตามลำดับ dependency ทดสอบ flow ข้ามคู่ด้านล่าง และบันทึกบั๊กพร้อมผู้แก้ — เกียร์ประสาน ทุกคู่ช่วยทดสอบ
- [ ] **INT-02 — Regression:** แก้บั๊กที่ขัด Acceptance Criteria ทดสอบซ้ำด้วยข้อมูลเริ่มต้นใหม่ บันทึกผลจริงและข้อจำกัด — เจ้าของ US + ผู้ตรวจต่างคู่
- [ ] **INT-03 — Demo/Docs:** เดโมจาก branch รวมที่ทีมตกลง อัปเดตวิธีรันและรายงาน Sprint ระบุงานที่เสร็จ/ย้ายออกพร้อมเหตุผล และ retrospective — ทั้งทีม

### Definition of Done

- [ ] Acceptance Criteria ของแต่ละ US ถูกยืนยันและผ่านครบ รวมงานเชื่อมต่อที่อยู่ในขอบเขต
- [ ] มีผลทดสอบกรณีสำเร็จ ข้อมูลผิด และสิทธิ์ พร้อมหลักฐานใน PR/ตารางข้างต้น
- [ ] ผ่าน review จากอีกคู่ แก้ conflict และ merge แล้ว
- [ ] มี migration/seed และคู่มือรันที่ใช้ได้จริงตามงานที่เปลี่ยน
- [ ] ไม่มีบั๊กค้างที่ทำให้ flow ที่ตกลงไว้ใช้ไม่ได้
- [ ] งานที่ยังไม่เสร็จถูกระบุเป็นงานค้างพร้อมผู้รับผิดชอบ ไม่ปิดเป็น Done หรือซ่อนด้วยการลด Acceptance Criteria ภายหลัง
